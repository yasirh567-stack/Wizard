# Wizard — Risk Register

**Last updated:** 2026-09-11
**Owner:** Yasir Hassan (solo project — every risk below is mine to own)

| # | Risk | Likelihood | Impact | Mitigation | Status |
|---|---|---|---|---|---|
| 1 | Categorization errors propagate — a confidently-wrong category poisons recurring-detection, forecasting, and any recommendation built on top of it. | Medium | High | Manual override is P0, not deferred (WIZ-8); categorization ships with a measured precision/recall against a held-out set (Phase 2 exit criteria) instead of an assumed-good black box; confidence is shown, not hidden. | Open — assess after Phase 2 |
| 2 | Plaid *Sandbox* data doesn't fully resemble real bank data (cleaner merchant names, fewer edge cases, no real multi-institution weirdness), so code that looks robust against sandbox data might not be. | Medium | Medium | Documented explicitly here and in `ARCHITECTURE.md` rather than assumed away; the synthetic seed dataset (WIZ-3) is deliberately built with messier data — irregular intervals, ambiguous merchant strings — specifically to stress-test beyond what sandbox alone would catch. | Accepted, mitigated partially |
| 3 | Scope creep — ten PRD features plus a PM Agent plus an experimentation framework all sound worth building at once, the same trap flagged in Momentum's risk register. | High | High | `ROADMAP.md` sequences this into 9 phases with stated exit criteria; `BACKLOG.md` priority tags (P0/P1/P2) mean "build this now?" has a written answer before the temptation hits, not an in-the-moment judgment call. | Mitigated by design |
| 4 | LLM chat layer (WIZ-17) hallucinates a number instead of computing it — the single worst failure mode for a finance product, since a wrong dollar figure is actively harmful, not just unhelpful. | Medium | High | Tool-calling architecture, not prompt-stuffing: the model calls the real forecast/recommendation functions and reports their output, it doesn't generate financial figures itself. WIZ-17's acceptance criteria requires every numeric claim to trace to an actual tool result — checked explicitly in Phase 4, not assumed from the architecture alone. | Open — assess after Phase 4 |
| 5 | The PM Agent (Phase 6+) trains its "research" on synthetic telemetry and synthetic support tickets — its prioritization and PRDs are only as good as how realistic that synthetic behavior is, and it can't be validated against real users at any point. | High | Medium | Disclosed everywhere the agent's output is presented (same standard as `METRICS.md`'s honesty note); the synthetic-user behavior model is itself documented (Phase 6 PRD) so its assumptions are inspectable, not a black box the agent's conclusions get laundered through. | Accepted, permanent limitation |
| 6 | Running Postgres + Redis + Celery + a separate PM Agent process is real operational surface for a solo dev to keep working reliably through months of intermittent development. | Medium | Medium | Docker Compose is the only supported local setup (one command, not a multi-step manual environment); CI (Phase 8) catches breakage from dependency/version drift between sessions before it's discovered mid-demo. | Open — assess after Phase 8 |
| 7 | Secrets (Plaid keys, Anthropic API key, DB credentials, JWT signing key) end up committed or logged, even in a portfolio project with sandbox-only data. | Low | High | `.env`/`.env.*` gitignored from commit 1 (this repo's very first `.gitignore`); `.env.example` documents required vars with placeholder values only; a pre-Phase-8 pass checks no secret ever appears in a log statement. | Mitigated by design |
| 8 | The research underneath `PRD.md`/`PERSONAS.md` is secondary desk research, not primary interviews — personas are directional guesses about what would help, not validated ones. | High | Medium | Disclosed explicitly in `USER_RESEARCH.md` rather than presented as if real interviews happened; the experimentation framework (Phase 7) is what actually validates or invalidates these assumptions against (synthetic) behavioral outcomes — treated as a hypothesis to test, not a fact already established. | Accepted, addressed in Phase 7 |
| 9 | AWS costs (RDS, ElastiCache, compute) run unattended between sessions that could be weeks apart, racking up idle spend on a project with no revenue. | Medium | Low | Deploy target and cost controls (auto-pause / scale-to-zero where available, or a teardown script) get decided in Phase 8 before anything long-lived goes up — not left as a surprise on a first AWS bill. | Open — assess in Phase 8 |
